The RenderPipeline and RenderPassNode classes form NullGraph's high-level render orchestration system. RenderPassNode defines a logical render pass with its attachments and draw batches, while RenderPipeline executes a sequence of passes — handling indirect draw reset, compute-based instance culling, main screen pass resolution, and final command submission to the GPU.

RenderPassNode (Class)

Represents a single logical render pass in the frame graph. It holds the pass's color and depth attachments, a list of render batches to execute, and metadata including whether this pass writes directly to the HTML canvas.

Constructor

new RenderPassNode(config)

Creates a new render pass node with the specified configuration.

  • config (RenderPassConfig):
    Configuration object specifying the pass name, target type, and optional custom attachments.

Configuration Interface

RenderPassConfig (Interface)

  • name: string
    A descriptive name for the render pass (e.g., "ShadowMap", "GBuffer", "Forward"). Used for debugging and identification in the pipeline.
  • isMainScreenPass: boolean
    If true, the render pipeline will automatically resolve this pass's color attachment to the HTML canvas's current texture and use the engine's default depth texture. Custom colorAttachments and depthStencilAttachment are ignored when this flag is set.
  • colorAttachments?: GPURenderPassColorAttachment[]
    Optional. Custom color attachments for offscreen rendering (e.g., G-Buffer targets, post-processing textures). Ignored if isMainScreenPass is true.
  • depthStencilAttachment?: GPURenderPassDepthStencilAttachment
    Optional. Custom depth/stencil attachment (e.g., for shadow map passes). Ignored if isMainScreenPass is true.

Public Properties

  • name: string
    The pass name as provided in the configuration.
  • isMainScreenPass: boolean
    Whether this pass renders directly to the swap chain / HTML canvas.
  • batches: RenderBatch[]
    The ordered array of render batches to execute during this pass. Each batch contains pipeline state, bind groups, buffers, and instance count.
  • colorAttachments: GPURenderPassColorAttachment[]
    The resolved color attachments for this pass. For main screen passes, this is populated by the pipeline just before rendering; for offscreen passes, it is taken from the configuration.
  • depthStencilAttachment?: GPURenderPassDepthStencilAttachment
    The resolved depth/stencil attachment, if any.

Batch Management

addBatch(batch)

Appends a render batch to this pass's execution list.

  • batch (RenderBatch):
    The render batch to add.
  • Returns: void

Batches are executed in insertion order during rendering.

removeBatch(batch)

Removes a render batch from this pass's execution list.

  • batch (RenderBatch):
    The render batch to remove. Must be the same object reference that was previously added.
  • Returns: void

Behavior

  • Locates the batch in the internal array using reference equality (indexOf).
  • If found, removes it via splice.
  • If the batch is not present in the array, the method silently does nothing.

RenderPipeline (Class)

Executes a sequence of RenderPassNode instances, translating them into WebGPU command buffers and submitting them to the device queue. It handles two critical pre-render steps: resetting indirect draw instance counts for GPU-culled batches, and dispatching compute shaders for instance culling.

Constructor

new RenderPipeline(ctx)

Creates a new render pipeline bound to a WebGPU context.

  • ctx (WebGPUContext):
    The WebGPU context providing the device, canvas context, and default depth texture.

Public Methods

render(passes)

Executes the full render sequence for the given array of render passes.

  • passes (RenderPassNode[]):
    An ordered array of render passes to execute. Empty arrays cause an early return with no GPU work submitted.
  • Returns: void

Execution Pipeline

For each RenderPassNode in the array, the pipeline performs the following sequence:

Phase 1: Indirect Draw Reset

Before any rendering, the pipeline scans all batches in the current pass for those marked as indirect (batch.isIndirect === true). For each such batch:

  • Writes zero to the indirect buffer's instanceCount field (offset 4 bytes — the second uint32 in the drawIndexedIndirect structure). This resets the instance count so that if the compute culling shader does not write a new count, the draw call will render zero instances.
  • Flags the pass as requiring a compute phase (hasCompute = true).

The zero value is written using a shared Uint32Array([0]) to minimize allocations across all resets.

Phase 2: Compute Pass (Instance Culling)

If the pass contains any indirect batches (hasCompute === true), a single compute pass is opened. For each indirect batch:

  • Sets the batch's compute pipeline and bind group (binding 0).
  • Sets any additional custom compute bind groups (bindings 1+).
  • Calculates the workgroup count as ceil(currentInstanceCount / 64).
  • Dispatches the compute shader if the workgroup count is greater than zero.

This compute phase is responsible for GPU-side frustum/occlusion culling — testing each instance and writing the surviving count and indices into the indirect buffer.

Phase 3: Attachment Resolution

The pass's color and depth attachments are resolved based on the isMainScreenPass flag:

  • Main Screen Pass (isMainScreenPass === true):
    • Color: Uses the canvas's current texture view (via ctx.context.getCurrentTexture().createView()) with a dark gray clear color ({r: 0.05, g: 0.05, b: 0.05, a: 1.0}), loadOp: 'clear', and storeOp: 'store'.
    • Depth: Uses the engine's shared depth texture view with a clear value of 1.0, depthLoadOp: 'clear', and depthStoreOp: 'store'.
    • Any custom attachments from the pass configuration are ignored.
  • Offscreen Pass (isMainScreenPass === false):
    • Uses the custom colorAttachments and depthStencilAttachment directly from the pass configuration.

Phase 4: Render Pass Execution

A render pass encoder is opened with the resolved attachments. For each batch in the pass:

  1. Skip Empty Static Batches: If the batch is not indirect and its currentInstanceCount is 0, it is skipped entirely.
  2. Set Pipeline: passEncoder.setPipeline(batch.pipeline)
  3. Set Bind Groups:
    • Bind group 0 is always set from batch.bindGroup.
    • Additional bind groups (1+) are set from batch.customBindGroups, keyed by string group indices parsed as integers.
  4. Set Buffers:
    • Vertex buffer at slot 0: batch.vertexBuffer (if set).
    • Index buffer: batch.indexBuffer with the batch's indexFormat (if set).
  5. Issue Draw Call (mutually exclusive — determined by available data):
    • Indirect Indexed: drawIndexedIndirect(batch.indirectBuffer, 0) — Used when batch.isIndirect is true and an indirect buffer is present. The GPU reads draw parameters from the buffer.
    • Direct Indexed: drawIndexed(indexCount, instanceCount, 0, 0, 0) — Used when both vertex and index buffers are present and the batch is not indirect.
    • Direct Non-Indexed: draw(3, instanceCount, 0, 0) — Fallback for batches without index buffers (e.g., fullscreen triangles for post-processing). Always draws 3 vertices.

Phase 5: Submission

After all passes have been encoded, the command buffer is finished and submitted to the device queue:

this.ctx.device.queue.submit([commandEncoder.finish()]);

All passes in the array are submitted together in a single command buffer, ensuring they execute in order on the GPU timeline.

Render Batch Structure

RenderBatch (Interface — from "./types")

The RenderBatch object is the fundamental unit of work within a render pass. Its expected shape includes:

Property Type Description
pipeline GPURenderPipeline The render pipeline state to use for drawing
bindGroup GPUBindGroup The primary bind group (group 0) — typically camera/engine uniforms
customBindGroups Record<string, GPUBindGroup> Optional additional bind groups (group 1+), keyed by group index as string
vertexBuffer GPUBuffer Vertex buffer at slot 0
indexBuffer GPUBuffer Index buffer
indexFormat GPUIndexFormat Format of the index buffer ('uint16' or 'uint32')
indexCount number Number of indices for direct indexed draws
currentInstanceCount number Current instance count for direct draws; also used to calculate compute workgroup count
isIndirect boolean Whether this batch uses indirect drawing (GPU-driven instance count)
indirectBuffer GPUBuffer The indirect draw buffer (present if isIndirect is true)
computePipeline GPUComputePipeline Compute pipeline for instance culling (present if isIndirect is true)
computeBindGroup GPUBindGroup Primary compute bind group (group 0) for culling
computeCustomBindGroups Record<string, GPUBindGroup> Optional additional compute bind groups (group 1+)

Typical Workflow

import { WebGPUContext } from './WebGPUContext';
import { RenderPipeline } from './RenderPipeline';
import { RenderPassNode } from './RenderPass';

// Create pipeline
const ctx = new WebGPUContext(/* ... */);
const pipeline = new RenderPipeline(ctx);

// Define passes
const shadowPass = new RenderPassNode({
    name: 'ShadowMap',
    isMainScreenPass: false,
    colorAttachments: [],  // No color output for shadow pass
    depthStencilAttachment: {
        view: shadowDepthView,
        depthClearValue: 1.0,
        depthLoadOp: 'clear',
        depthStoreOp: 'store',
    }
});

const mainPass = new RenderPassNode({
    name: 'Main',
    isMainScreenPass: true  // Renders directly to canvas
});

// Add batches to passes
shadowPass.addBatch(shadowBatch);
mainPass.addBatch(skyboxBatch);
mainPass.addBatch(opaqueBatch);
mainPass.addBatch(transparentBatch);

// Execute each frame
function frame() {
    pipeline.render([shadowPass, mainPass]);
}

Execution Order Summary

For a pipeline with passes [PassA, PassB, PassC], the GPU timeline is:


PassA: [Indirect Reset] → [Compute Culling] → [Render Attachments] → [Draw Batches]
PassB: [Indirect Reset] → [Compute Culling] → [Render Attachments] → [Draw Batches]
PassC: [Indirect Reset] → [Compute Culling] → [Render Attachments] → [Draw Batches]
                                                                          │
                                                                    [GPU Submit]

All phases for all passes are encoded into a single command buffer and submitted atomically. The GPU executes passes sequentially with full pipeline barriers between them.
